# JavaScript Bất Đồng Bộ - Xử Lý Công Việc Mà Không Phải "Chờ Dài Cổ"

Chào các bạn! Trong thế giới lập trình, đặc biệt là với JavaScript - "trái tim" của các ứng dụng web tương tác - không phải lúc nào các công việc cũng diễn ra một cách tuần tự "xong việc này mới đến việc kia". Sẽ có những tác vụ tốn thời gian, ví dụ như tải dữ liệu từ server, đọc file, hoặc đợi người dùng click chuột. Nếu JavaScript cứ "đứng hình" chờ những việc đó xong xuôi, trải nghiệm người dùng sẽ cực kỳ tệ hại.

Đây chính là lúc **lập trình bất đồng bộ (asynchronous programming)** tỏa sáng! Nó cho phép JavaScript "giao việc" cho một ai đó (ví dụ: trình duyệt, hệ điều hành) và tiếp tục làm những việc khác trong khi chờ kết quả. Khi nào việc được giao hoàn thành, JavaScript sẽ được thông báo và xử lý kết quả đó.

Trong bài này, chúng ta sẽ cùng nhau khám phá hành trình của JavaScript từ những "lời hẹn" đơn giản với Callbacks, tìm hiểu "cỗ máy thời gian" Event Loop, làm quen với "lời hứa chắc nịch" Promises, và cuối cùng là "cú pháp thần tiên" `async/await`. Nắm vững những khái niệm này sẽ giúp bạn xây dựng những ứng dụng web mượt mà, nhanh nhạy và không bao giờ để người dùng phải "chờ dài cổ"!

## Đồng Bộ (Synchronous) vs. Bất Đồng Bộ (Asynchronous) - Ai Trước Ai Sau?

Để hiểu bất đồng bộ, trước tiên hãy nói về "người anh em" của nó: đồng bộ.

### 1. Code Đồng Bộ (Synchronous Code)

Trong code đồng bộ, các câu lệnh được thực thi **tuần tự, từ trên xuống dưới**. Câu lệnh sau phải chờ câu lệnh trước thực thi xong hoàn toàn rồi mới đến lượt mình. Giống như xếp hàng mua vé, người sau phải đợi người trước mua xong.

```javascript
console.log("1. Bắt đầu mua vé.");

// Giả sử đây là một tác vụ tốn thời gian (ví dụ: xử lý hình ảnh nặng)
// Trong code đồng bộ thực sự, hàm này sẽ "block" (chặn) các dòng tiếp theo.
function xuLyCongViecTonThoiGian() {
  let startTime = Date.now();
  while (Date.now() - startTime < 3000) {
    // Giả lập công việc 3 giây
    // Đang làm việc chăm chỉ...
  }
  console.log("2. Xử lý công việc nặng đã xong!");
}
xuLyCongViecTonThoiGian();

console.log("3. Cuối cùng cũng xong việc xếp hàng!");
// Thứ tự output:
// 1. Bắt đầu mua vé.
// (chờ 3 giây)
// 2. Xử lý công việc nặng đã xong!
// 3. Cuối cùng cũng xong việc xếp hàng!
```

Nếu `xuLyCongViecTonThoiGian()` thực sự là một tác vụ nặng, toàn bộ trang web có thể bị "treo" trong 3 giây đó. Không ổn chút nào!

### 2. Code Bất Đồng Bộ (Asynchronous Code)

Trong code bất đồng bộ, một số tác vụ có thể được "ủy quyền" để chạy ở "hậu trường". JavaScript không chờ chúng hoàn thành mà tiếp tục thực thi các câu lệnh tiếp theo. Khi nào tác vụ "hậu trường" đó xong, nó sẽ thông báo (thường là qua một callback, promise, hoặc event) để JavaScript xử lý kết quả.

```javascript
console.log("1. Bắt đầu nấu cơm.");

// setTimeout là một ví dụ về hàm bất đồng bộ
setTimeout(function () {
  // Hàm này (callback) sẽ được gọi sau khi 2 giây trôi qua
  console.log("3. Cơm đã chín! Mời cả nhà xơi!");
}, 2000); // 2000ms = 2 giây

console.log("2. Trong lúc chờ cơm chín, đi rửa rau.");

// Thứ tự output:
// 1. Bắt đầu nấu cơm.
// 2. Trong lúc chờ cơm chín, đi rửa rau.
// (sau khoảng 2 giây)
// 3. Cơm đã chín! Mời cả nhà xơi!
```

Bạn thấy đó, chương trình không bị chặn. "Rửa rau" được thực hiện ngay mà không cần chờ "cơm chín". Đây chính là sức mạnh của bất đồng bộ, đặc biệt quan trọng cho các tác vụ như:

- **Yêu cầu mạng (Network requests):** Tải dữ liệu từ API, gửi form.
- **Thao tác I/O (Input/Output):** Đọc/ghi file.
- **Timers:** `setTimeout`, `setInterval`.
- **Sự kiện người dùng (User events):** Click chuột, gõ phím.

### 3. Event Loop: "Nhạc Trưởng" Của Bất Đồng Bộ

Vậy làm thế nào JavaScript (vốn là đơn luồng - single-threaded) có thể xử lý bất đồng bộ? Câu trả lời nằm ở **Event Loop (Vòng Lặp Sự Kiện)** và sự phối hợp với các thành phần khác như Call Stack và Message Queue (còn gọi là Callback Queue hoặc Task Queue).

Đây là một mô hình đơn giản hóa:

1.  **Call Stack (Ngăn Xếp Lệnh Gọi):** Nơi JavaScript theo dõi các hàm đang được thực thi. Khi một hàm được gọi, nó được đẩy vào stack. Khi hàm kết thúc, nó được lấy ra khỏi stack.
2.  **Web APIs / Node.js APIs:** Đây là nơi các tác vụ bất đồng bộ thực sự được xử lý (ví dụ: `setTimeout`, `fetch` được trình duyệt hoặc Node.js quản lý, không phải engine JavaScript). Khi một tác vụ bất đồng bộ (như `setTimeout`) được gọi, nó được "gửi" đến API tương ứng.
3.  **Message Queue (Hàng Đợi Tin Nhắn / Callback Queue):** Khi một tác vụ bất đồng bộ hoàn thành (ví dụ: timer của `setTimeout` kết thúc, dữ liệu từ API về tới), hàm callback tương ứng của nó sẽ được đưa vào Message Queue, xếp hàng chờ đến lượt.
4.  **Event Loop (Vòng Lặp Sự Kiện):** Đây là một vòng lặp vô tận. Nhiệm vụ của nó là liên tục kiểm tra xem Call Stack có **rỗng** không. Nếu Call Stack rỗng _và_ Message Queue có gì đó đang chờ, Event Loop sẽ lấy "tin nhắn" (callback) đầu tiên từ Message Queue và đẩy nó vào Call Stack để thực thi.

Mô hình này cho phép JavaScript không bị "block" bởi các tác vụ dài hơi. Trong khi Web API xử lý tác vụ đó, JavaScript có thể tiếp tục làm việc khác. Khi tác vụ xong, callback của nó kiên nhẫn chờ trong Message Queue cho đến khi Call Stack rảnh rỗi.

## Callbacks: "Lời Hẹn" Cho Tương Lai

Trước khi có những "anh hùng" xịn sò như Promises hay async/await, **callbacks** chính là "người hùng thầm lặng" giúp JavaScript xử lý các tác vụ bất đồng bộ.

Hiểu nôm na, callback là một hàm được "truyền như một món quà" (tham số) cho một hàm khác. Hàm nhận "món quà" này sẽ "hứa" rằng: "Ok, tôi sẽ làm việc của tôi trước, khi nào xong (hoặc có kết quả gì đó), tôi sẽ gọi lại hàm bạn đưa nhé!"

### "Alo, Xong Việc Rồi Gọi Lại Nhé!"

Hãy xem ví dụ kinh điển với `setTimeout`, hàm này sẽ thực thi một callback sau một khoảng thời gian nhất định:

```javascript
console.log("1. Bắt đầu công việc nè!");

// `handleTimeout` là callback function
function handleTimeout() {
  console.log("2. A lô, sau 2 giây Cò đã gọi lại!");
}

setTimeout(handleTimeout, 2000); // 2000 milliseconds = 2 giây

console.log("3. Trong lúc chờ Cò gọi, tôi làm việc khác...");
```

Chạy thử code trên, bạn sẽ thấy thứ tự in ra là:

1. Bắt đầu công việc nè!
2. Trong lúc chờ Cò gọi, tôi làm việc khác...
   (Sau khoảng 2 giây)
3. A lô, sau 2 giây Cò đã gọi lại!

Thấy không? `setTimeout` không "block" (chặn) chương trình. Nó nhận callback `handleTimeout` và "hẹn" 2 giây sau sẽ gọi. Trong thời gian đó, code vẫn chạy tiếp tới dòng `console.log` thứ ba.

**Ví dụ khác: Xử lý sự kiện click chuột (Event Listener)**

```html
<button id="myButton">Bấm Em Đi!</button>
<script>
  const button = document.getElementById("myButton");

  // `handleClick` là callback, sẽ được gọi KHI button được click
  function handleClick() {
    console.log("Button đã được bấm!");
  }

  button.addEventListener("click", handleClick); // Đăng ký callback cho sự kiện click

  console.log("Đã đăng ký sự kiện click. Chương trình vẫn chạy tiếp...");
</script>
```

Callback `handleClick` chỉ được thực thi khi sự kiện `click` xảy ra.

### "Địa Ngục Callback" (Callback Hell / Pyramid of Doom)

Callbacks rất hữu ích, nhưng khi bạn có nhiều tác vụ bất đồng bộ phụ thuộc lẫn nhau (tác vụ B chỉ chạy sau khi A xong, C chỉ chạy sau khi B xong,...), code của bạn có thể biến thành một "kim tự tháp" các hàm lồng vào nhau. Điều này làm code rất khó đọc, khó hiểu và khó bảo trì. Người ta hay gọi vui (mà cũng buồn) là **"Callback Hell"** hay **"Pyramid of Doom"**.

```javascript
// Ví dụ minh họa "Callback Hell" (code giả tưởng, đừng làm theo nhé!)
// Tưởng tượng bạn cần lấy thông tin user, rồi lấy bài viết của user, rồi lấy comment của bài viết
getUser(userId, function (err, user) {
  if (err) {
    console.error("Lỗi lấy user:", err);
  } else {
    console.log("Thông tin user:", user);
    getPosts(user.id, function (err, posts) {
      if (err) {
        console.error("Lỗi lấy posts:", err);
      } else {
        console.log("Các bài viết:", posts);
        getComments(posts[0].id, function (err, comments) {
          if (err) {
            console.error("Lỗi lấy comments:", err);
          } else {
            console.log("Các bình luận:", comments);
            // Và cứ thế lồng vào nhau... nếu có thêm bước nữa
            // Khó đọc, khó debug, khó quản lý lỗi!
          }
        });
      }
    });
  }
});
```

Nhìn đã thấy "ớn lạnh" rồi phải không? Chính vì vấn đề nan giải này mà **Promises** và sau đó là **async/await** ra đời để "giải cứu" chúng ta khỏi "địa ngục" này.

## Promises: "Lời Hứa" Đáng Tin Cậy

Promises (Lời hứa) được giới thiệu trong ES6 (ES2015) như một giải pháp thanh lịch hơn cho việc xử lý bất đồng bộ so với callbacks. Một Promise là một đối tượng đặc biệt, đại diện cho **kết quả (hoặc lỗi) của một thao tác bất đồng bộ sẽ diễn ra trong tương lai**.

Hãy tưởng tượng bạn đặt hàng online. Cửa hàng (hàm bất đồng bộ) sẽ đưa cho bạn một "phiếu hẹn" (Promise). Phiếu hẹn này có thể có 3 trạng thái:

1.  **Pending (Đang chờ):** Trạng thái ban đầu, chưa biết thành công hay thất bại. (Đơn hàng đang được xử lý).
2.  **Fulfilled (Hoàn thành / Thành công):** Thao tác bất đồng bộ đã hoàn thành thành công, và có một giá trị kết quả. (Đơn hàng đã giao thành công, bạn nhận được món hàng).
3.  **Rejected (Bị từ chối / Thất bại):** Thao tác bất đồng bộ đã thất bại, và có một lý do (lỗi). (Đơn hàng bị hủy, bạn nhận được thông báo lỗi).

Một khi Promise đã chuyển sang `fulfilled` hoặc `rejected`, trạng thái của nó sẽ **không bao giờ thay đổi nữa**.

### Tiêu Thụ Promises: `then()`, `catch()`, `finally()`

Để làm việc với kết quả (hoặc lỗi) của một Promise, chúng ta sử dụng các phương thức:

- **`.then(onFulfilled, onRejected)`**:
  - `onFulfilled`: Một hàm callback sẽ được gọi nếu Promise chuyển sang trạng thái `fulfilled`. Nó nhận giá trị kết quả làm đối số.
  - `onRejected` (tùy chọn): Một hàm callback sẽ được gọi nếu Promise chuyển sang trạng thái `rejected`. Nó nhận lý do lỗi làm đối số.
- **`.catch(onRejected)`**: Một cách viết gọn hơn và dễ đọc hơn cho việc xử lý lỗi, tương đương với `.then(null, onRejected)`. Nó sẽ bắt lỗi từ Promise trước đó hoặc bất kỳ lỗi nào trong chuỗi `.then` trước nó.
- **`.finally(onFinally)`**: Một hàm callback sẽ **luôn luôn** được gọi sau khi Promise đã "settled" (tức là đã `fulfilled` hoặc `rejected`), bất kể kết quả ra sao. Thường dùng để dọn dẹp tài nguyên (ví dụ: tắt loading spinner).

```javascript
// Giả lập một hàm tải dữ liệu trả về Promise
function taiDuLieu(thanhCong = true) {
  return new Promise((resolve, reject) => {
    console.log("Bắt đầu tải dữ liệu...");
    setTimeout(() => {
      if (thanhCong) {
        let duLieu = { id: 1, ten: "Dữ liệu quan trọng" };
        resolve(duLieu); // Lời hứa hoàn thành -> fulfilled
      } else {
        let loi = new Error("Không thể tải được dữ liệu!");
        reject(loi); // Lời hứa thất bại -> rejected
      }
    }, 2000);
  });
}

// Tiêu thụ Promise khi thành công
taiDuLieu(true)
  .then((data) => {
    // onFulfilled
    console.log("Dữ liệu nhận được:", data);
    // Bạn có thể trả về một giá trị hoặc một Promise khác ở đây để chaining
    return data.ten.toUpperCase();
  })
  .then((tenVietHoa) => {
    // onFulfilled cho Promise trả về từ .then() trước
    console.log("Tên viết hoa:", tenVietHoa);
  })
  .catch((error) => {
    // onRejected (sẽ không chạy trong trường hợp này)
    console.error("Có lỗi xảy ra:", error.message);
  })
  .finally(() => {
    console.log(
      "Quá trình tải dữ liệu đã kết thúc (dù thành công hay thất bại)."
    );
  });

// Tiêu thụ Promise khi thất bại
/*
taiDuLieu(false)
  .then(data => {
    console.log("Dữ liệu nhận được (sẽ không chạy):", data);
  })
  .catch(error => { // Lần này catch sẽ chạy
    console.error("Lỗi rồi bạn ơi:", error.message);
  })
  .finally(() => {
    console.log("Dọn dẹp sau khi tải thất bại.");
  });
*/
```

### Chaining Promises (Nối Chuỗi Lời Hứa)

Một trong những ưu điểm lớn của Promises là khả năng "nối chuỗi" (chaining). Phương thức `.then()` (và `.catch()`) bản thân nó cũng trả về một Promise mới, cho phép bạn thực hiện các thao tác bất đồng bộ nối tiếp nhau một cách rõ ràng, tránh được Callback Hell.

Nếu callback trong `.then()` trả về:

- **Một giá trị thông thường:** Promise mới sẽ ngay lập tức `fulfilled` với giá trị đó.
- **Một Promise khác:** Promise mới sẽ "theo dõi" Promise được trả về này, và sẽ `fulfilled` hoặc `rejected` tương ứng với kết quả của Promise đó.

```javascript
function buoc1() {
  return new Promise((resolve) =>
    setTimeout(() => {
      console.log("Bước 1 xong");
      resolve(10);
    }, 1000)
  );
}

function buoc2(giaTriTuBuoc1) {
  console.log("Nhận từ bước 1:", giaTriTuBuoc1);
  return new Promise((resolve) =>
    setTimeout(() => {
      console.log("Bước 2 xong");
      resolve(giaTriTuBuoc1 * 2);
    }, 1000)
  );
}

function buoc3(giaTriTuBuoc2) {
  console.log("Nhận từ bước 2:", giaTriTuBuoc2);
  return new Promise((resolve) =>
    setTimeout(() => {
      console.log("Bước 3 xong");
      resolve(giaTriTuBuoc2 + 5);
    }, 1000)
  );
}

buoc1()
  .then((ketQua1) => buoc2(ketQua1)) // buoc2 trả về Promise, .then() tiếp theo chờ Promise này
  .then((ketQua2) => buoc3(ketQua2))
  .then((ketQuaCuoiCung) => {
    console.log("Kết quả cuối cùng của chuỗi:", ketQuaCuoiCung); // 25
  })
  .catch((err) => console.error("Lỗi trong chuỗi:", err));
```

Code dễ đọc hơn hẳn so với Callback Hell phải không nào?

### Tạo Ra Promises: `new Promise((resolve, reject) => { ... })`

Bạn có thể tự tạo ra một Promise bằng cách sử dụng constructor `new Promise()`. Nó nhận một hàm (executor function) làm đối số. Hàm executor này lại nhận hai hàm khác làm đối số: `resolve` và `reject`.

- Bên trong hàm executor, bạn thực hiện thao tác bất đồng bộ của mình.
- Khi thành công, gọi `resolve(value)` để chuyển Promise sang `fulfilled` với `value`.
- Khi thất bại, gọi `reject(error)` để chuyển Promise sang `rejected` với `error`.

Ví dụ `taiDuLieu` ở trên đã minh họa cách tạo Promise.

### Các Phương Thức Tĩnh Hữu Ích Của `Promise`

Đối tượng `Promise` cũng cung cấp một số phương thức tĩnh (static methods) tiện lợi:

- **`Promise.all(iterable)`**: Nhận một iterable (thường là một mảng) các Promises. Trả về một Promise mới sẽ:

  - `fulfilled` khi **tất cả** các Promises trong iterable `fulfilled`. Giá trị `fulfilled` là một mảng chứa kết quả của tất cả các Promises đó (theo đúng thứ tự ban đầu).
  - `rejected` ngay khi **một trong số** các Promises trong iterable `rejected`. Lý do `rejected` là lý do của Promise bị `rejected` đầu tiên.
    Rất hữu ích khi bạn cần thực hiện nhiều tác vụ bất đồng bộ song song và chỉ muốn tiếp tục khi tất cả đều xong.

  ```javascript
  const p1 = Promise.resolve(3);
  const p2 = 1337; // Giá trị không phải Promise sẽ được coi là Promise đã fulfilled
  const p3 = new Promise((resolve, reject) => setTimeout(resolve, 100, "foo"));
  const p4_error = Promise.reject("Lỗi ngay!");

  Promise.all([p1, p2, p3])
    .then((values) => console.log("Promise.all thành công:", values)) // [3, 1337, "foo"]
    .catch((err) => console.error("Promise.all thất bại:", err));

  // Promise.all([p1, p4_error, p3])
  //   .then(values => console.log("Sẽ không chạy:", values))
  //   .catch(err => console.error("Promise.all thất bại do p4_error:", err)); // "Lỗi ngay!"
  ```

- **`Promise.race(iterable)`**: Nhận một iterable các Promises. Trả về một Promise mới sẽ `fulfilled` hoặc `rejected` ngay khi **Promise đầu tiên** trong iterable `fulfilled` hoặc `rejected`. "Ai chạy nhanh nhất thì thắng!"

  ```javascript
  const promiseA = new Promise((resolve) =>
    setTimeout(resolve, 500, "A thắng!")
  );
  const promiseB = new Promise((resolve, reject) =>
    setTimeout(reject, 100, "B thua nhanh!")
  );

  Promise.race([promiseA, promiseB])
    .then((winner) => console.log("Promise.race:", winner)) // "B thua nhanh!" (vì reject sau 100ms)
    .catch((loserReason) => console.error("Promise.race (lỗi):", loserReason)); // Nếu promiseB resolve thì đây sẽ là winner
  ```

- **`Promise.resolve(value)`**: Trả về một Promise đã `fulfilled` với `value` được cung cấp. Nếu `value` là một Promise, thì Promise đó sẽ được trả về.
- **`Promise.reject(reason)`**: Trả về một Promise đã `rejected` với `reason` được cung cấp.

## `async/await` (ES2017): Viết Code Bất Đồng Bộ Như Đồng Bộ

Mặc dù Promises đã cải thiện đáng kể so với callbacks, việc viết nhiều `.then()` lồng nhau đôi khi vẫn có thể hơi khó theo dõi. `async/await` là một lớp "đường cú pháp" (syntactic sugar) nữa được xây dựng **trên nền tảng Promises**, giúp bạn viết code bất đồng bộ trông giống như code đồng bộ, dễ đọc và dễ hiểu hơn rất nhiều.

### Từ Khóa `async`

Khi bạn đặt từ khóa `async` trước một khai báo hàm, nó sẽ biến hàm đó thành một **hàm bất đồng bộ (async function)**. Một hàm `async` luôn ngầm trả về một Promise.

- Nếu hàm `async` trả về một giá trị, Promise sẽ `fulfilled` với giá trị đó.
- Nếu hàm `async` ném ra một lỗi (throw an error), Promise sẽ `rejected` với lỗi đó.

```javascript
async function chaoBuoiSang() {
  return "Chào buổi sáng!"; // Promise sẽ fulfilled với "Chào buổi sáng!"
}

chaoBuoiSang().then((loiChao) => console.log(loiChao)); // Chào buổi sáng!

async function hamLoi() {
  throw new Error("Ối, lỗi rồi!"); // Promise sẽ rejected với Error này
}

hamLoi().catch((err) => console.error(err.message)); // Ối, lỗi rồi!
```

### Từ Khóa `await`

Từ khóa `await` chỉ có thể được sử dụng **bên trong một hàm `async`**. Khi bạn đặt `await` trước một Promise, nó sẽ **tạm dừng** việc thực thi của hàm `async` đó cho đến khi Promise đó "settled" (tức là `fulfilled` hoặc `rejected`).

- Nếu Promise `fulfilled`, `await` sẽ trả về giá trị `fulfilled` đó.
- Nếu Promise `rejected`, `await` sẽ ném ra (throw) lỗi `rejected` đó (giống như `throw error`).

```javascript
function layDuLieuSau2Giay(giaTri) {
  return new Promise((resolve) => {
    setTimeout(() => {
      console.log(`Đã lấy xong: ${giaTri}`);
      resolve(giaTri);
    }, 2000);
  });
}

async function xuLyCongViec() {
  console.log("Bắt đầu công việc...");

  const ketQua1 = await layDuLieuSau2Giay("Dữ liệu A"); // Dừng ở đây chờ Promise giải quyết
  console.log("Kết quả 1 nhận được:", ketQua1);

  const ketQua2 = await layDuLieuSau2Giay("Dữ liệu B sau " + ketQua1); // Dừng tiếp
  console.log("Kết quả 2 nhận được:", ketQua2);

  const ketQua3 = await layDuLieuSau2Giay("Dữ liệu C sau " + ketQua2);
  console.log("Kết quả 3 nhận được:", ketQua3);

  return `Hoàn thành với: ${ketQua3}`;
}

console.log("Trước khi gọi xuLyCongViec");
xuLyCongViec()
  .then((finalResult) => console.log("Promise từ xuLyCongViec:", finalResult))
  .catch((err) => console.error("Lỗi từ xuLyCongViec:", err.message));
console.log("Sau khi gọi xuLyCongViec (nhưng chưa chạy xong bên trong nó)");

// Thứ tự output sẽ là:
// Trước khi gọi xuLyCongViec
// Bắt đầu công việc...
// Sau khi gọi xuLyCongViec (nhưng chưa chạy xong bên trong nó)
// (2 giây sau)
// Đã lấy xong: Dữ liệu A
// Kết quả 1 nhận được: Dữ liệu A
// (2 giây sau)
// Đã lấy xong: Dữ liệu B sau Dữ liệu A
// Kết quả 2 nhận được: Dữ liệu B sau Dữ liệu A
// (2 giây sau)
// Đã lấy xong: Dữ liệu C sau Dữ liệu B sau Dữ liệu A
// Kết quả 3 nhận được: Dữ liệu C sau Dữ liệu B sau Dữ liệu A
// Promise từ xuLyCongViec: Hoàn thành với: Dữ liệu C sau Dữ liệu B sau Dữ liệu A
```

### Xử Lý Lỗi với `try...catch` trong `async/await`

Vì `await` sẽ ném ra lỗi nếu Promise bị `rejected`, bạn có thể sử dụng khối `try...catch` quen thuộc để bắt và xử lý các lỗi này, giống như trong code đồng bộ.

```javascript
async function taiDuLieuNguoiDung(userId) {
  try {
    console.log(`Bắt đầu tải thông tin cho user ID: ${userId}`);
    // Giả sử fetchUserData trả về một Promise
    // const response = await fetch(`https://api.example.com/users/${userId}`);
    // if (!response.ok) {
    //   throw new Error(`Lỗi HTTP: ${response.status}`);
    // }
    // const userData = await response.json();

    // Giả lập với Promise tự tạo
    const userData = await new Promise((resolve, reject) => {
      setTimeout(() => {
        if (userId === 1) {
          resolve({ id: 1, ten: "Alice" });
        } else {
          reject(new Error("Không tìm thấy người dùng!"));
        }
      }, 1000);
    });

    console.log("Thông tin người dùng:", userData);
    return userData;
  } catch (error) {
    console.error(`Không thể tải dữ liệu người dùng: ${error.message}`);
    // throw error; // Bạn có thể ném lại lỗi nếu muốn hàm gọi xử lý tiếp
    return null; // Hoặc trả về giá trị mặc định
  } finally {
    console.log(`Kết thúc việc tải dữ liệu cho user ID: ${userId}`);
  }
}

async function chayThu() {
  await taiDuLieuNguoiDung(1); // Thành công
  console.log("---");
  await taiDuLieuNguoiDung(2); // Thất bại, lỗi sẽ được catch bên trong taiDuLieuNguoiDung
}
chayThu();
```

Cách viết này thường được coi là dễ đọc và dễ quản lý hơn so với việc dùng nhiều `.catch()` trong chuỗi Promise.

### Lợi Ích Của `async/await`

- **Dễ đọc, dễ hiểu:** Code trông gần giống code đồng bộ, giúp giảm độ phức tạp nhận thức.
- **Xử lý lỗi gọn gàng:** Dùng `try...catch` quen thuộc.
- **Debug dễ hơn:** Khi debug, call stack sẽ dễ theo dõi hơn so với chuỗi Promises.

Nhớ rằng, `async/await` không thay thế Promises, mà là một cách tốt hơn để làm việc với chúng. Bên dưới, nó vẫn là Promises!

## Tổng Kết

Lập trình bất đồng bộ là một phần không thể thiếu của JavaScript hiện đại, giúp tạo ra các ứng dụng web nhanh nhạy và không bị "đứng hình". Chúng ta đã đi từ những **Callbacks** cơ bản, hiểu được cơ chế hoạt động của **Event Loop**, rồi đến **Promises** với khả năng xử lý lỗi và chaining mạnh mẽ. Cuối cùng, **`async/await`** xuất hiện như một "lớp áo choàng" tuyệt đẹp, giúp chúng ta viết code bất đồng bộ một cách thanh lịch và dễ đọc như code đồng bộ.

Việc nắm vững các khái niệm này sẽ mở ra cho bạn cánh cửa để xây dựng những ứng dụng phức tạp, tương tác cao và mang lại trải nghiệm tốt nhất cho người dùng. Hãy thực hành nhiều với các ví dụ, thử thách bản thân với các kịch bản bất đồng bộ khác nhau, và bạn sẽ sớm làm chủ được "nghệ thuật" này!
